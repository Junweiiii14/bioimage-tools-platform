# WB 全批原值裁剪门槛 v5

T081：新整批顺序计划使用 `intake_workflow@5`。填写的 N、槽位身份、原像素、
裁剪算法版本、测量公式、存储 CAS 和已发布历史目录不由此策略改变。

某行 crop 待复核、失败或中断不妨碍其他 pending crop 按清单顺序尝试。全部必需行
的 crop 都实际 done，且同一行保存了当前来源 SHA、有效几何、匹配的 ROI 与原值
裁图资产后，才允许领取任何 compose、measure 或 export 票据。仅有候选、已采纳
几何、done 字样或其他 Fig 的成功结果都不构成整批裁剪完成。原值文件仍经宿主
所属后台任务导出、资产导入、身份核验和正常 CAS 后完成阶段。

全部 crop 满足门槛后，compose 仍依赖本 Fig 完整成员，measure 依赖本 Fig 已保存
成图；export 需要全部 Fig 测量 done，不自动发布失败批次的部分目录。显式项目
快照和结果表导出在 v5 裁剪门槛未满足时同样拒绝。保存工作草稿继续可用。
`require_intake_crop_barrier` 为调度之外的统一发布前置校验：
`export_intake_outputs`（包括无票据调用）、`finalize_intake_delivery` 和
`export_intake_table` 在创建文件、临时目录或调用材料归位前均检查它。拒绝时
不创建目标，已存在阶段目录也不增写。`materialize_intake_delivery` 仍允许逐行
归位原图和已完成原值裁剪；它不构成最终项目发布。v1–v4 发布行为保持兼容。
用户取消仍取消整批，失败不会形成无限重试。修改或重试一行只使该行及其所属 Fig
依赖和最终输出过期，已经成功的其他 crop 不重新领取、不重写原值资产。

旧 v1–v4 文件读取和直接按旧策略运行保持原行为；打开项目不迁移。现有项目的
“继续处理（先完成全部裁剪）”和重试动作携带明确 `cropBarrier=true`，通过
`adopt_intake_crop_barrier(project, expected_digest=...)` 创建 v5 当前修订，随后
正常保存再执行。`continue_intake_sequence(..., use_crop_barrier=True)` 共用此
用例，缺省 False 保留旧调用语义。过期摘要、运行中和编辑中迁移拒绝。

迁移保留原有步骤尝试、成功 crop、Fig 与测量证据及历史输出；不把其他 Fig 的
旧成功当成本批完成。只要仍有 crop 缺口，新调度与显式导出就停在裁剪阶段。
已完整完成的旧项目不因继续动作改版本，也不会重算历史。执行后明确修正产生
新修订时可再采用 v5。新旧项目规则均不能将缺失或失败变成有效零值。

`intake_workflow_snapshot.crop_barrier_ready` 是从真实保存证据推导的只读状态，
不是持久化可写成功标志。界面在 v5 缺口存在时保留配置与裁剪入口；拼图、灰度与
结果阶段在门槛满足后启用。安装自检观察活动阶段时也核对全批原值裁剪依赖。

验证覆盖两种失败终态、其余 crop 继续、done 无资产不放行、修正后成功行不重跑、
旧 v4 的读取与显式迁移、取消/摘要保护及真实页面入口。旧 v3 严格暂停和 v4
独立 Fig 部分输出测试固定旧策略，不能拿新默认策略改写旧契约。
