# 从实验需求到完整自动流程：开发流程

配合[主方案5.0](research-platform-rd.md)。每轮先完成普通实验人员的一项真实任务，再把已验证步骤开放给专业组合。以下是开发要求，不是已完成实验调研的报告。

## 1. 先写一张实验场景卡

在当前任务的证据目录维护一份场景卡，至少写明：使用者及经验、发生场景、任务频率、当前工具/耗时/失败、原始输入、样本/重复/分组、最终表图和用途、适用范围与不支持情况、资料来源和未决问题。

把事实分为实际观察、用户转述、公开来源和待验证假设。用户觉得“更简单”不能直接变成已证实的付费需求；公开教程不能冒充实验室实操。

结果定义先于界面和算法清单。例如计数任务需明确计数对象、重叠处理、面积/视野、单位和汇总层级；归一化需明确对照、分母失效和重复身份。科学语义不明确时列为待决，不由文件名、UI默认值或Agent补齐。

## 2. 观察一条完整操作链

从导入到最终交付，记录每次有意义的处理、参数默认值、变化理由、输入输出及失败纠正。再拿另一批数据核对哪些步骤固定、哪些变化。只有获准使用的数据进入实验；私有原图不提交仓库。

| 动作类别 | 自动化方式 | 必须显式保留 |
|---|---|---|
| 固定计算 | 直接调用已验证算法 | 方法、版本、输入输出与单位 |
| 每批信息 | 导入清单或最少必要填写 | 样本身份、分组、对照与重复 |
| 数据驱动选择 | 经验证的估参/判断规则 | 本次计算值、依据、适用范围与失败 |
| 科学判断未定 | 暂停相应结论，提供复核入口 | 不能可靠自动判断的原因 |
| 展示和排版 | 独立显示处理与导出 | 不修改定量来源或伪造实验身份 |

不把每一次点击都变成节点。保留一条能被解释的处理链即可；正常样本不逐步骤请求确认。

## 3. 做算法复用核验和最小对照

任何新算法研发或现有简易基线继续优化之前，先检索适用的成熟开源实现、官方pipeline及预训练模型；此要求同样适用于所有后续实验模块和算法研发Agent。已有项目实现要与成熟候选比较，不能默认自有简易基线优先。简单基线只作诊断对照，不代替选型。

按“检索候选→少量代表性数据真实调用→选择成熟且适用的实现→必要时才自研”推进。优先通过受支持API/CLI或封装官方实现直接复用，把开发重点放在完整实验流程与易用性。每个候选简短记录来源、固定版本/提交、代码与权重许可及分发条件、依赖、输入转换、默认参数、CPU/GPU/离线要求和维护风险。

先在小型冻结代表性样例上真实调用少量候选，比较效果、失败样例、CPU耗时及部署维护成本，检查中间资产和最终结果，再决定集成。需要第三方软件或模型时记录安装条件、权重/资源来源和错误返回，核查训练数据与评估数据重叠；未知重叠不能声称独立泛化。不把未运行候选标成可用。复用CellProfiler也必须实际调用并验证具体pipeline/模块及接口，自己复写同名算法不能称为复用；成熟方案仍须验证适用范围。

只有检索和最小实验证实现成方案不能满足具体需求或无法合理集成，才自行复现/研发，并在原任务证据中简短说明候选、具体不足及选择依据。尚未搜索、安装稍麻烦或单个候选失败均不是充分理由；先检查其他适用成熟候选或合理调用方式。不增加审批表或逐项用户确认。

对照应分开验证读取/转换、预处理、分割或定位、测量、归一化、汇总和导出。比较指标、参考来源和容差在看结果前固定；参考不能由新实现自己产生。保持失败样例，不通过删样本、改预期或扩大容差制造通过。

## 4. 先完成实验，再暴露专业模块

使用现有公开API、可信注册、冻结计划、worker及Workspace。先用已有完整步骤封装成实验模板，补上导入、必要信息、质量反馈、结果导出和重开。模板跑通后才按真实替换/复用需求细分模块，不另造执行器。

| 层次 | 交付内容 |
|---|---|
| 方法 | 公式或原实现适配、参数、适用范围、版本与参考 |
| 模块 | 输入/输出/单位/身份、失败状态、资源边界与测试 |
| 实验模板 | 默认步骤、必要信息、自动估参依据、质量门槛、成果规则 |
| 实验向导 | 以结果为中心的短路径、进度、异常与可选纠正 |
| 专业工作流 | 同一模块和模板的查看/替换/组合，不产生第二套计算 |

领域算法不读文件、不调用Qt/数据库/子进程；I/O放适配层，实验用例组合本工具方法，宿主负责进程和正式提交。图像位深、坐标、通道与尺度不丢失；跨工具只走公开API。

## 5. 自动化、异常和修正保持可复现

首次确定必要样本信息和方法配置后，正常路径自动运行。无法可靠判断的情况返回明确状态，不伪装成有效零或成功。按预设策略暂停当前样本或继续其余样本，运行结束列出成功、失败、待复核与排除情况。

纠正保存为新修订，重算受影响的步骤及下游；不会覆盖原始输入或历史成果。运行记录实际参数、原始/分析资产摘要、模块/方法/实现/环境版本和正式输出；模板只有明确保存才更新。

正式几何校正由版本化方法生成保精度分析资产，预览、ROI和定量绑定同一来源；旧显示旋转保持原有历史语义。方法变化与纯重构分开交付。

## 6. 两组验收，外加工程底线

方法验收：冻结开发/调参数据与独立验证数据，按来源/生物样本划分，避免同图裁片泄漏；保持独立参考、原始失败和适用范围。与原软件一致只证明指定配置下的复现，不能单独授予科学准入。

用户验收：让目标用户在明确任务和允许帮助条件下独立使用，记录完成数/总数、耗时、求助位置、误操作、错误发现及恢复。与现有处理基线比较，记录学习成本；首次小样本只作探索，不推导全体用户成功率。

工程底线：真实输入、取消、异常、重开、提交/导出一致，旧结果和原图受保护，目标负载及环境有证据。部分科学/目标环境缺项可以保留候选，不得把未验写成正式交付。

三者分别记入同一任务验收表。预先约定严重失败的处理规则；存在可能静默改变结论的错误时，先修复再让流程进入正式使用。

## 7. 一次任务如何结束

任务卡保留范围、状态、准确提交与验收结论；证据目录保留场景卡、方法来源、对照和使用记录。README只给“用户动作→公开API→用例/方法→输出→测试”的短导航，公式和方法只维护一个权威位置。

产品改动绑定准确提交独审，经现有PR与必需检查集成；旧数据兼容和未验项写清。未完成项说明影响、责任角色、解除条件与下一动作，而不是不断在当前方案尾部追加相互矛盾的说明。

同一实验出现参数差异先用预设；有真实方法差异再加模块。新实验连续需要平台特判、公式被复制或调用链难以追踪时，依据具体问题重构。维护细则见[维护计划](../maintenance-plan.md)。
