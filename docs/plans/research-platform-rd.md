## 1. 软件形态：实验室可编排的分析操作平台

产品像一套可视化宏：把实验人员在不同软件中反复进行的分析操作，封装成模块，连接成流程。用户可直接使用现成实验模板，也可换步骤、改参数，保存为本实验室模板。以后导入同类新数据，就能自动得到分析表和图片。

界面包含模块列表、流程画布、参数设置、运行状态和结果预览。模块既可以是已有算法，也可以是某软件的宏、脚本或受控调用。平台负责连接和执行，实验模块负责方法；不要求一开始重写ImageJ、Photoshop或Prism的全部功能。

**核心开发顺序是：看人怎样做 → 记录每个有意义的动作 → 查清实际算法 → 调用或复现算法 → 对照验证 → 封装模块 → 编排自动运行 → 用新数据持续验证。** 不能跳过真实工作，先凭想象堆算法节点。

## 2. 调研起点：观察真实操作，而不只收集软件名称

每次选一个具体场景，如“某实验室某类WB的相对蛋白表达分析”。先用已有授权材料，观察熟练人员从原始数据到最终结果的一次完整处理；拿到另一份数据，观察哪些动作发生变化。记录实际做法，也追问每次调整的理由。

| 观察内容 | 必须记录的事实 |
|---|---|
| 数据进入软件 | 仪器/文件、版本、通道、位深、样本和分组；导入时有无转换 |
| 点击和处理 | 软件功能、菜单/命令、先后顺序、输入输出、中间文件 |
| 设置与微调 | 显式参数及未改动的默认值、单位、选区、背景、阈值、排除对象 |
| 人员判断 | 看到什么才调整，按什么依据调整，什么时候认定失败 |
| 软件之间交接 | 导出列、格式、单位、精度、样本顺序，以及复制粘贴时做的计算 |
| 最终交付 | 结果表、图、统计设计、独立重复身份、保存和重开方式 |

把动作分为固定计算、参数选择、数据驱动规则、科学判断和排版操作。固定计算直接自动化；参数变成模板配置；有依据的判断变成明确规则；无法可靠表达的判断保留异常提示和可选纠正。显示处理与定量分开。

公开教程用于补充和核验，不能替代实验室操作记录。没有真实记录时可以先做候选原型，但必须标明尚未完成流程复现。调研不意味着未经授权联系他人或上传私有数据。

## 3. 复现方法：把动作还原成可验证的计算

对每一步查阅对应版本的官方文档、宏记录、可用源码或原始方法说明，弄清公式、处理顺序、参数默认值、坐标和边界规则。按钮同名不等于算法相同；结果相近也不能单独证明方法相同。

有三种实现路径，必须写清采用哪一种：

| 路径 | 什么时候用 | 可以宣称什么 |
|---|---|---|
| 直接调用原实现 | 有可用库、接口、命令行或宏 | 使用指定版本的原功能；仍需核验输入转换和调用设置 |
| 根据已知方法重新实现 | 原方法足够明确，适合本地实现 | 经指定数据和容差验证的方法复现，不承诺所有输入完全等价 |
| 新增替代方法 | 原实现不可用或细节未知，需要其他算法 | 明确命名的新方法，不标成“原软件同算法” |

优先复用已有能力或直接调用。不得凭空猜闭源功能的内部公式。只有确实缺少稳定调用方式时才评估界面自动化；也要检查真实输出，不能以“按钮点击完成”认定分析成功。

开发前固定一组原图、操作参数、关键中间结果和参考输出，预先确定比较指标与容差。先逐步对照，再对比最终结果：格式转换、选区、背景、测量、归一化分别查，不能只看最后的图像是否相似。参考值不得由新实现自己生成。

还要检查原方法是否适合当前实验。与原软件一致是复现证据，独立已知样例、标注或方法依据是科学适用性证据；两者分开。新数据验证失败时，定位失败步骤，修正后保留旧版本和失败样例。

详细记录与实施方式统一放在[真实操作到模块的开发流程](workflow-development.md)。

## 4. 模块与自动化：复用的是方法，不是鼠标坐标

一个模块对应一项有意义的处理，如背景扣除、区域测量、归一化或导出。一个动作可以对应多个计算步骤，一段连续宏也可以先整体封装；不要强制“一个点击一个节点”。

模块先声明输入、参数、输出、方法版本和失败结果。图像保留位深、通道与坐标，表格保留单位及样本身份。用薄适配连接原功能与现有执行器，不另建一套任务、缓存、恢复或保存系统。执行模块采用固定审核登记，不允许工作区任意代码直接加载。

实验室之间的差异按最小变化处理：参数不同用预设；方法不同换模块；顺序不同改连接；格式不同补读取适配；特殊流程可保留专用模块。只有两个真实消费者已证明稳定共性时，才提炼公共能力。

固定参数保存在模板；每批样本信息作为运行输入；有算法依据的参数由计算步骤产生，并保存本次计算值；有明确依据的选择保存条件和分支。规则按具体流程需要增加，不预建万能判断引擎，也不让Agent自由猜阈值。

首次配置时可检查和修正模板；日常正常样本默认全自动，不逐节点确认。异常样本保留原因，按已选策略暂停该样本或继续其他样本。纠正生成新修订，只重算受影响的下游，旧结果保留；只有明确保存才更新模板版本。

模板记录模块版本、连接、参数和输出规则；运行记录实际数据、实际参数、方法/实现/环境和正式成果。界面与命令行共用执行语义。Agent以后可以辅助配置和解释，不是此能力的前置条件。

## 5. 工程分区：每类代码有明确职责

沿用当前模块化单体、公开API、后台worker和现有工作区，不为规划提前新建空包。以下是职责分区，不是要求立刻搬移旧代码：

| 分区 | 现有位置 | 负责什么 | 不应放什么 |
|---|---|---|---|
| 通用契约 | `packages/tool_contracts/` | 文件/结果身份、节点输入输出、执行消息 | WB公式、界面、数据库操作 |
| 平台运行与存储 | `packages/platform_runtime/` | 通用图规则、执行账本、工作区事务与恢复 | 某实验特判、控件、工具内部调用 |
| 实验算法 | `tools/wb/.../domain/`；未来其他工具同样分层 | 纯数据和数值计算、方法定义 | 文件读写、Qt、进程和数据库 |
| 实验用例 | `tools/wb/.../application/` | 组合本工具算法，完成测量/归一化等动作 | 界面细节、跨工具内部引用 |
| 输入输出适配 | `tools/wb/.../adapters/` | TIFF/CSV、外部软件/worker、成果导出 | 第二套科学公式、第二套运行引擎 |
| 宿主与界面 | `apps/desktop/`、工具的`ui/` | 注册、后台任务接线、交互和展示 | 浏览器中偷偷算定量、UI线程重计算 |
| 测试和工程工具 | 包内`tests/`、根`tests/`、`tooling/` | 独立参考、集成验证、构建与检查 | 生产代码依赖测试工具或探针 |

跨包只走`package.api`。平台不认识“内参”“阳性细胞”等实验概念。现有桌面宿主负责进程/线程接线，不将其职责误塞进纯算法或平台图规则中。未来若需要共享图像包，应先证明实际复用，再按既有依赖边界接入。

人工审查从模块地图进入：**用户动作 → 公开入口 → 用例 → 算法/适配 → 结果提交 → 相关测试。** 每个模块README维护这条短路线；关键算法注明方法版本、数据含义和参考测试。注释解释“为什么”，不复述代码。

详见[长期维护与人工审查导航](../maintenance-plan.md)及其中的实际WB入口示例。

## 6. 长期维护：随功能交付，持续控制复杂度

代码能否长期推进，不能靠一次整理保证。维护要随每个功能切片执行：方法有依据、职责清楚、变化可验证、历史可恢复、下一位维护者找得到入口。

- **一次改一个完整行为。** 调研、方法变更、功能接线、无关重构和依赖升级不要混成一大包；相互依赖的最小改动可以一起交付。
- **简单实现优先。** 入口验证后内部信任类型；只处理已知异常；不用静默兜底掩盖失败；不为假想扩展堆配置、接口和继承层。
- **重构有触发条件。** 同一公式被复制、一个文件混合不相干职责、增加实验总要改平台特判、旧事件反复覆盖新状态，才按具体原因拆分。长文件是检查信号，不是机械拆碎的理由。
- **审查能顺着代码读。** PR说明行为变化、入口与关键函数、验证及兼容；独审绑定准确提交，后续相关更改重新审查。不要求每个小提交重新审批。
- **升级不改变旧答案。** 公式/默认值/预处理影响结果时版本化；旧模板不静默换方法。格式迁移先备份，在副本验证，保留恢复路线。
- **维护有节奏。** 每任务检查相关行为；每里程碑看高频故障和复杂模块，做接手与恢复检查；依赖定期人工复核，固定版本升级。没有自动创建后台调度。

测试按风险选择：公式看独立数值参考，接口看实际数据交换，执行看失败/取消/提交，界面看真实交互，安装看独立环境。先定向，最终候选完成既有必需检查；不为文档改动重复全套产品测试，不为过门禁削弱断言。

技术债记在对应任务，交接只保留入口。记录问题造成的具体影响、处理触发条件、责任角色和完成证据；关键正确性/数据风险当次处理，普通整理按计划推进，不借“维护”无限扩大范围。

WB实例已明确：旧工作台具备裁图、多峰、基线、归一化和导出；新工作流先有原图校验、分析、发布三个节点。下一步依次做真实方法对照、接入现有归一化、补样本/重复汇总，再按真实需要补背景/总蛋白/统计等能力。正式新几何沿P-004，不由显示旋转冒充。

## 8. 验收：既看结果，也看代码能否继续维护

一条流程交付时，应能回答六个问题：对应人员的哪些动作？采用什么方法和版本？结果与什么参考比较？新数据能否按模板运行？失败和纠正怎样处理？维护者从哪里进入代码并验证修改？

验收分三条记录：**工程能运行、方法有证据、人员能使用。** 不以测试数量替代科学验证，也不把缺少一类科学材料变成无关工程的停工条件。输出应可追溯到原始输入，失败和缺失不能伪装成0或成功。

可维护性的完成证据包括：入口与调用链可定位，算法没有重复权威实现，边界检查通过，相关测试可执行，README/契约与代码同次更新，旧数据兼容范围清楚。文档完整不代表这些检查已经完成。
