## 维护节奏

每任务开始核对规则、状态和最小基线；先跑受影响模块的定向测试，交付前再做完整检查和独审，收尾更新任务与交接。每周人工检查依赖/机器人PR/积压缺陷；每里程碑做独审、恢复演练和冷启动接手；每次候选发布执行 release.md 完整矩阵。没有自动通知或后台调度。

## 给使用者的维护说明

- 日常从桌面“BioImage WB 工作台（当前开发）”启动；启动器固定自身目录，默认与历史常用参数进入现有绿色工作台。旧原生工具只走显式兼容入口，测试默认离屏。每次维护先确认活动分支/提交，历史目录不冒充当前版本。
- 图像识别、数值计算、界面和存储按模块隔离。修一个问题先定位所属模块，避免连带重写其他功能；公共接口和依赖检查尽早发现跨模块乱接。
- 修 bug 的顺序是：保留出错样本和旧结果→复现并写回归用例→最小修改→相关测试→完整检查与真实图验证→独立复核→小范围 PR 集成。每项有任务、命令、退出码和提交记录，不能只凭一句“测试通过”。
- 原图和完成结果不覆盖；代码提交、旧结果和原未提交文件分别保留。Git备份不包含私有原图，原资料须另行备份；恢复演练和最终安装包验收仍须完成。
- 8张真实原图回归是当前已知问题的检查集，参考仅用于识别结束后评分；积分待复核和独立留出科学验收仍如实保留。测试数量不等于任何实验图都一定正确。

报 bug 时保留四项即可：从哪个入口启动及版本、出错前的操作步骤、预期与实际结果、可复现的原图或项目副本。截图用于说明界面；原图和原项目保留，复现使用副本。维护者先据日志和模块图定位，再把这次问题加入回归检查，后续修改自动检查是否复发。无法复现或缺少科学真值时，明确记录待确认项，不用猜测结果代替修复。

## 前端技能的使用边界

Taste 与 Impeccable 用作设计/审查辅助，固定来源后使用；二者冲突时以项目任务和既有设计体系为准。当前绿色HTML工作台由 PySide6/QtWebEngine 承载，保持既有产品入口，不因技能引入 React、GSAP或远程字体。科研界面优先清晰、键盘可用、原值/显示可区分、错误可解释、无干扰动效。网页浏览器验收不能替代 Qt/DPI 验收。

## 社区项目学习

源码可用时优先固定提交、阅读公开API/测试/调用链，提炼一个问题并做最小独立实验。仅在打包产物、原生扩展或运行时行为缺乏源码证据时考虑 REA；结论必须能指向源码/符号/实验，不以反编译推测替代科学定义。

## T-044：本轮维护机制更新（2026-10-18）

本轮继续使用绿色工作台，补齐首页目录筛选、同Fig分组、独立灰度曲线与人工边界调整、审核后原文件夹回存。启动脚本以隔离Python启动，并核验实际导入的代码目录和界面资源；安装指向别处就明确停止，避免悄悄打开历史工作树。它不能识别所有外部旧快捷方式，日常仍统一使用“BioImage WB 工作台（当前开发）”。

本轮把两个已有操作共用的显示裁剪/图像发布过程合并；按调用链检查123个产品Python文件，删除确认不用的局部控件、前端监听和10条样式规则。旧项目schema1–8和实际仍用的兼容入口保留。公开API延迟加载显示依赖，独立核心安装用例检查不加载Pillow，防止开发环境有依赖而安装包缺依赖的情况再次漏过。大宿主文件仍是后续维护热点，按新增操作逐步拆分，不一次重写。

维护分工：用户负责说明操作步骤、预期结果和确认实验语义；维护者负责复现、最小修复、验证和整理PR；独立审查者复核提交与关键反例。每次需求对应任务单和规则回执，每次发布候选都保留旧版本与资料备份。

修bug固定流程：①保留原图/项目副本与旧结果，记录入口、版本、步骤和错误；②根据模块图与阶段日志定位；③先建立能复现错误的用例；④仅修改相关模块；⑤相关测试、完整门禁、真实图流程和提交绑定独审；⑥提交小范围PR，远端检查通过并按阶段集成；⑦更新任务、日志和交接。这样下一次修改可以自动检查同类问题是否复发，不能保证任何未知bug都能立刻修完。

定期维护仍为人工执行，没有新增后台自动调度：每周检查依赖漏洞/机器人PR/缺陷；依赖更新独立提交并核验锁文件；里程碑执行资料恢复和接手演练，候选包执行干净Windows与DPI/真实交互验收。Git保存代码，私有原图和忽略结果须另行备份。

当前限制：8张原图属于开发回归集，裁图历史严格评分1/8→8/8，本轮正常工作台结果逐源几何及显示像素与已评分结果一致；不能外推所有设备。48槽由7有效/41待复核变为13有效/35待复核，背景不足21→2；保留原像素零值风险，不代表积分准确率。没有独立积分真值，扩大背景上限的反例有明显偏差，未发布。间歇原生退出根因仍有UNKNOWN，不能以单次完整通过销账。设计sidecar/PRODUCT过时、全DPI验收、恢复演练和最终发布安装包仍列后续事项。

测试环境也纳入生命周期管理：只清理测试自己创建并拥有的窗口，先等后台完成，再在界面线程确认原生窗口销毁；失败保留为失败。共用测试清理函数和错误路径回归，避免测试遗留对象干扰后续检查，不把全局删除或关闭垃圾回收当修复。原生异常的历史证据仍保留，未证实的因果不销账。
